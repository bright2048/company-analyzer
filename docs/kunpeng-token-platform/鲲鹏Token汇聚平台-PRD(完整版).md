## 第1章 项目概述

### 1.1 项目背景
随着大模型技术的快速普及，越来越多的企业和开发者需要接入 AI 能力。然而，各大模型商（字节、智谱、minimax、百度文心、阿里通义、腾讯混元、DeepSeek、月之暗面等）的接口协议、鉴权方式、定价体系各异，给用户带来极大的接入成本和管理复杂度。
国内大模型市场在 2025 年至 2026 年间经历了剧烈的价格战和技术迭代 [1] [2]。新兴厂商如 **DeepSeek** 以极具颠覆性的价格和强大的推理能力打破了市场格局，而 **月之暗面 (Moonshot AI)** 凭借 Kimi 的超长上下文和 Agent 编程能力也在企业级市场占据重要地位 [2] [3]。
在这一背景下，企业在采购大模型 API 时面临以下三大核心痛点：
1. **多厂商接入成本高**：各厂商 API 接口、SDK 各异，切换模型需要重构代码。
2. **资金管理繁琐**：需要向多家厂商分别预充值，资金占用多，发票报销流程繁琐。
3. **高可用保障难**：单一厂商服务可能出现限速、宕机，缺乏自动故障转移机制。

鲲鹏公司基于此市场机会，推出 **Token 汇聚平台**，为用户提供一个统一的 AI 调用网关，屏蔽各厂商差异，支持灵活套餐购买和 token 消费管理，打造“一次接入，全网通达”的极简体验。

### 1.2 项目目标
* **统一接入**：方便接入各大主流 AI 厂商的 token 服务，提供 100% 兼容 OpenAI 标准的 API 接口，实现无缝切换。
* **高可用与弹性**：提供多通道负载均衡和自动故障转移，保障生产环境的高可用性。
* **极佳 C 端体验**：提供面向开发者的简洁购买和使用体验，包括套餐选购、余额管理、多 API Key 管理、多维度用量看板。
* **专业 B 端支持**：支持组织/团队协作、对公转账、增值税发票开具，满足企业合规采购刚需。
* **精细化运营**：提供功能强大的运营管理后台，支持套餐设计、优惠券发放、多维度用户行为与毛利分析。

### 1.3 商业模式与定价策略
平台采用“**聚合批发 + 智能路由 + 增值服务**”的商业模式：
1. **聚合批发差价**：平台通过大批量采购各厂商 Token 获得官方折扣或大客户优惠，零售给用户时，通过平台统一定价或微调定价获取差价。
2. **汇率与额度优势**：针对国际模型，提供极具竞争力的结算汇率（如 1元=1美元 的额度补贴或极低汇率差），吸引国内开发者 [4]。
3. **增值服务费**：对企业级客户提供专线加速、多组织管理、私有化部署、安全审计等增值服务，收取订阅费或服务费。

### 1.4 术语说明

| 术语 | 英文名称 | 说明 |
| :--- | :--- | :--- |
| **Token** | Token | AI 模型处理文本的计量单位，约 4 个英文字符或 2 个中文字符为 1 token。 |
| **适配器** | Adapter | 对接特定厂商 API 协议的适配器模块，将其转换为标准 OpenAI 格式。 |
| **钱包** | Wallet | 用户账户内的余额，购买套餐后到账，调用时按量扣减。系统内部采用微美元精度。 |
| **微美元** | Micro-USD | 计费单位，等于 $10^{-6}$ 美元，用于避免浮点数精度误差。 |
| **套餐** | Plan | 可购买的 token 套餐，以人民币定价，到账 USD 额度。 |
| **优惠券** | Coupon | 优惠券，支持固定额度、折扣、赠 token 三种类型。 |
| **流式响应** | SSE / Streaming | Server-Sent Events，允许模型生成内容时实时向客户端推送，实现打字机效果。 |
| **故障转移** | Failover | 当主供应商接口异常时，系统自动切换到备用供应商的机制。 |

### 2.2 核心使用场景

#### 场景一：开发者极速接入与多 Key 管理
* **流程**：个人开发者注册账号后，获得系统赠送的初始测试额度。进入控制台，自助创建了两个 API Key（一个用于开发环境，一个用于生产环境），并为开发 Key 设置了每日消费上限以防代码死循环。开发者将代码中的 `base_url` 指向鲲鹏网关，填入 API Key，即刻开始调用。

#### 场景二：企业团队协作与合规采购
* **流程**：某 AI 初创公司 CTO 注册企业账号，在平台选购了“企业包（¥1499）”，通过企业支付宝完成支付。CTO 在后台创建了“智能客服项目”和“内部 RAG 项目”两个组织，邀请了 5 名开发人员加入，并为每个项目分配了固定的消费配额。月底，CTO 在控制台一键提交了发票申请，系统自动开具了增值税电子普通发票发送至其邮箱。

#### 场景三：高并发场景下的智能路由与自动故障转移
* **流程**：在晚高峰时段，某企业调用量骤增。系统主通道（如 字节跳动豆包）由于瞬时并发过高出现 429 限速错误。网关层检测到异常，在 50ms 内自动将后续请求路由到备用通道（如 阿里通义 Qwen），用户端无任何报错，首字时延仅轻微波动，业务完全未受影响。

#### 场景四：多模态与长上下文应用
* **流程**：开发者需要处理一份 50 万字的合同。他调用统一网关的 `chat/completions` 接口，指定使用支持超长上下文的模型（如 `kimi-k2.5` 或 `qwen3.5-plus`），并开启流式响应。网关自动适配上游协议，将长文本和流式数据稳定传输，帮助用户快速生成合同分析报告。

## 第3章 功能需求

### 3.1 用户注册、认证与安全防刷
平台采用先进的双令牌体系，保障管理侧与消费侧的安全隔离。
1. **客户管理令牌 (X-Admin-Token)**：用户在网页端登录后生成，用于在控制台进行创建 API Key、购买套餐、查询账单等管理操作。
2. **API Key (Bearer Token)**：调用 AI 网关和查询用量数据时使用，格式为 `kp-xxxxxxxxxxxxxxxxxxxxxxxx`。

#### 3.1.1 注册接口
* **安全防刷机制**：注册接口必须集成 **Cloudflare Turnstile** 或网易易盾等第三方人机校验。严禁仅凭邮箱直接注册赠送余额，防止黑产批量注册刷取免费额度。
* **注册参数**：
  - `email` (string, 必填)：用户邮箱，唯一键，注册后不可修改。
  - `password` (string, 必填)：密码，需满足复杂度要求（8-20位，含大小写字母和数字）。
  - `company` (string, 选填)：公司名称。
  - `turnstile_token` (string, 必填)：人机校验 Token。

### 3.2 供应商接入层 (Provider Adapter)

#### 3.2.1 数据模型扩展
为支持更复杂的计费和管理，供应商模型在原设计基础上进行了升级：

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| **ID** | string | 供应商通道唯一标识，如 `supplier-deepseek-v3` |
| **Name** | string | 显示名称，如 "DeepSeek 官方通道" |
| **Protocol** | string | 协议类型：`openai` / `baidu` / `qwen` / `hunyuan` / `spark` / `mock` |
| **BaseURL** | string | API 端点地址，空时使用各协议默认地址 |
| **APIKey** | string | 厂商鉴权 Key（**必须使用 AES-256-GCM 加密存储**） |
| **SecretKey** | string | 百度文心或特定厂商专用 Secret Key（加密存储） |
| **Model** | string | 默认映射模型名称 |
| **InputPrice** | float64 | 供应商输入成本（每百万 Token，USD） |
| **OutputPrice** | float64 | 供应商输出成本（每百万 Token，USD） |
| **CacheHitPrice** | float64 | 缓存命中输入成本（如 DeepSeek 缓存命中特惠价，每百万 Token，USD） |
| **Priority** | int | 路由优先级，数值越小越优先（1-100） |
| **Weight** | int | 负载均衡权重（1-100），同优先级下按权重分配流量 |
| **Status** | string | 状态：`active` (启用) / `disabled` (禁用) / `degraded` (降级，仅允许只读或低频) |

#### 3.2.2 扩展供应商协议适配
平台需支持以下主流厂商的适配器（Adapter）：
1. **DeepSeek Adapter**：
   - 适配 `deepseek-chat` (V3.2/V4) 和 `deepseek-reasoner` (R1) [2] [5]。
   - **核心支持**：必须适配其**上下文缓存 (Context Caching)** 计费，当响应体中包含 `prompt_tokens_details.cached_tokens` 时，应按 `CacheHitPrice` 进行成本结算 [5]。
2. **月之暗面 (Kimi) Adapter**：
   - 适配 `kimi-k2.5` / `kimi-k2.6` 等长文本和推理模型 [2] [3]。
   - **核心支持**：支持最大 256k-1M 的上下文窗口传输，支持 `thinking` 模式的输出适配 [2]。
3. **讯飞星火 (Spark) Adapter**：
   - 适配星火 V3.0/V4.0。
   - **核心支持**：由于星火官方部分接口采用 WebSocket 协议，适配器需在网关层实现 WebSocket 转 HTTP 协议的长连接保持与流式数据转换。
4. **阿里通义 (Qwen) Adapter**：
   - 适配 DashScope 的 OpenAI 兼容模式，支持 `qwen3-max`、`qwen3.5-plus` 等模型 [2]。
5. **字节跳动 (豆包) Adapter**：
   - 适配火山引擎 API，支持其极致高并发的调用模式。

#### 3.2.3 智能路由与故障转移 (Failover) 规则
* **健康检查 (Ping)**：系统每 30 秒向所有 active 供应商发送轻量级检测请求（或通过历史调用成功率统计）。
* **自动降级与恢复**：当某通道连续 3 次请求返回 5xx 错误或超时（>10s），系统自动将其状态标记为 `degraded`，并将其优先级临时降至最低。连续 10 分钟无报错后，自动恢复其原始优先级。
* **无感知切换**：网关在发起调用时，若遇到非用户原因（如 500, 502, 503, 504, 429）的失败，**必须自动重试下一个优先级的通道**。仅当所有可用通道均尝试失败，或用户余额不足、请求格式错误（4xx）时，才向用户返回错误。
* **重试上限**：单次请求最大自动重试次数为 3 次，避免请求链路过长导致客户端超时。
## 第3章 功能需求 (续)

### 3.3 统一调用网关 (LLM Gateway)

#### 3.3.1 核心路由接口
* **入口**：`POST /v1/proxy/chat/completions`
* **协议兼容**：100% 兼容 OpenAI Chat Completions 规范，支持传入 `model`、`messages`、`stream`、`temperature`、`max_tokens`、`tools` (Function Calling) 等参数。
* **模型映射机制**：用户传入的 `model` 参数（如 `kp-gpt-4o`、`kp-deepseek-r1`）在网关层通过映射表动态解析为对应供应商的真实模型 ID。

#### 3.3.2 流式响应 (SSE) 支持
* **技术实现**：当用户请求设置 `stream: true` 时，网关层必须采用 **Server-Sent Events (SSE)** 协议与客户端保持长连接。
* **流式计费**：网关需实时解析上游返回的 chunk 数据。在连接结束（收到 `[DONE]` 信号）时，从最后一个数据 chunk（或通过网关层自主统计 token 数）中提取 `usage` 数据，并扣减用户钱包余额。
* **首字延迟目标**：网关自身的流式转发延迟必须 $\le 10\text{ms}$，首字呈现延迟 $\le 300\text{ms}$。

#### 3.3.3 多模态与辅助接口
1. **向量化接口 (Embeddings)**：
   - `POST /v1/proxy/embeddings`：用于 RAG（检索增强生成）场景，支持统一封装国内外的向量化模型。
2. **图像生成接口 (Text-to-Image)**：
   - `POST /v1/proxy/images/generations`：兼容 OpenAI 格式，支持路由到 Midjourney、DALL-E 3 或国内主流生图模型。
3. **语音转文字接口 (Speech-to-Text)**：
   - `POST /v1/proxy/audio/transcriptions`：支持 Whisper 或国内主流语音识别模型。

### 3.4 钱包、计费与高精度控制

#### 3.4.1 微美元 (Micro-USD) 高精度计费
为彻底解决浮点数计算在多并发扣费时产生的精度丢失和对账不一致问题，系统底层存储和计费引擎统一采用**微美元 (Micro-USD, 简写为 $\mu\text{USD}$)** 作为货币单位：
$$\text{1 USD} = 1,000,000\ \mu\text{USD}$$
在数据库（PostgreSQL）中，钱包余额字段 `balance` 必须使用 **`BIGINT`** 类型存储，所有扣费、充值、对账逻辑均在整数维度进行，仅在前端展示时除以 $10^6$ 转换为标准 USD 格式。

#### 3.4.2 扣费与原子性保障
* **扣费公式**：
  $$\text{扣费金额} = (\text{输入 Token 数} \times \text{平台输入单价}) + (\text{输出 Token 数} \times \text{平台输出单价})$$
  若触发上游缓存命中（如 DeepSeek 缓存），则输入 Token 中命中缓存的部分按平台缓存特惠单价计费。
* **原子操作**：在高并发调用下，扣费必须通过数据库行锁（`SELECT FOR UPDATE`）或 Redis 分布式锁保障原子性。
* **预扣费机制**：为防止恶意透支，网关在收到请求时，需根据 `max_tokens`（若未传则按默认值，如 2048）估算最大可能消费金额。若用户当前余额低于该预估值，直接拒绝请求并返回 `402 Payment Required`。

#### 3.5.3 购买与支付流程
1. **外部支付集成**：Phase 2 必须集成**微信支付**和**支付宝**。

   - 写入 `purchases` 购买记录。
   - 增加 `wallets` 表中对应的微美元余额。
   - 若套餐有有效期限制，在 `user_limits` 表中记录该笔额度的到期时间，计费引擎优先扣减有有效期的额度（先进先出，FIFO）。

### 3.6 优惠券体系 (Coupon System)

#### 3.6.1 优惠券数据模型
为防止优惠券被滥用，对优惠券模型进行严谨的重构：

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| **ID** | string | 券唯一标识 |
| **Code** | string | 唯一券码（如 `WELCOME2026`） |
| **Type** | string | `fixed_credit` (固定额度) / `discount` (充值折扣) / `gift_tokens` (赠送Token) |
| **Value** | int64 | 优惠值（固定额度为微美元；折扣为百分比 1-99；赠Token为具体数量） |
| **MinSpend** | int64 | 最低充值金额要求（单位：分，仅对折扣券有效） |
| **MaxUses** | int | 全局最大可核销次数（0 表示不限） |
| **UsedCount** | int | 全局已核销次数 |
| **UserLimit** | int | 单用户最大可核销次数（默认 1 次） |
| **ExpiresAt** | time.Time | 过期时间 |
| **Status** | string | `active` / `disabled` |

#### 3.6.2 核销与防刷风控
* **核销幂等性**：用户核销优惠券时，必须通过数据库唯一索引 `unique_user_coupon(user_id, coupon_id)` 保证单个用户无法重复核销同一张券。
* **行为审计**：每次核销成功，必须向 `coupon_use_records` 写入详细的审计日志，包含核销时间、IP 地址、设备指纹等，便于后续风控排查。

## 第4章 非功能性需求与系统指标

### 4.1 性能与高并发指标 (Performance)
* **网关吞吐量**：AI 路由网关层设计并发处理能力 $\ge 5000\text{ QPS}$。网关层必须采用无状态设计，支持水平弹性扩容。
* **极低网关时延**：网关自身的路由解析、鉴权、风控校验、计费统计等核心链路耗时必须 $\le 10\text{ms}$（不含上游模型响应时间）。
* **流式响应时延**：在流式传输（SSE）模式下，首字呈现时延（TTFT - Time to First Token）必须 $\le 300\text{ms}$（在网络状况良好的情况下，依赖上游响应速度）。

### 4.2 系统可用性与 SLA (Availability)
* **服务可用性目标**：平台整体服务可用性 $\ge 99.95\%$。
* **高可用架构**：
  - 数据库采用主从热备，支持秒级自动切换。
  - 引入 Redis 哨兵或集群模式，保障缓存层的高可用。
  - 网关层部署于多可用区（Multi-AZ），结合 SLB（负载均衡）实现流量分发。

### 4.3 安全性需求 (Security)
1. **传输安全**：所有外部 API 请求及控制台访问必须强制使用 **HTTPS (TLS 1.3)** 加密传输。
2. **敏感数据加密**：
   - 用户的密码必须使用 **bcrypt** 或 **Argon2** 算法进行单向哈希存储，严禁明文存储。
   - 供应商 API Key、Secret Key 等敏感凭证，在数据库中必须使用 **AES-256-GCM** 算法进行对称加密存储，密钥由外部密钥管理系统（如 HashiCorp Vault）统一托管。
3. **接口防刷与 DDoS 防护**：
   - 接入 Cloudflare 或阿里云高防，清洗恶意 DDoS 流量。
   - 对敏感接口（登录、注册、短信验证码、优惠券核销）实施严格的单 IP 限频。

### 4.4 法律与内容合规性需求 (Compliance)
1. **数据合规**：平台需严格遵守《中华人民共和国数据安全法》及《个人信息保护法》，默认不存储用户请求的 Prompt 及模型返回的 Response 具体文本，仅记录 Token 计量、耗时、模型 ID 等计费元数据。
2. **内容安全审查 (Moderation)**：
   - **核心刚需**：为符合国内监管要求，网关层必须内置或集成合规的内容安全过滤引擎（如接入网信办备案的内容安全审核 API）。
   - **双向拦截**：对用户输入的 Prompt 和模型输出的 Response 进行实时敏感词过滤。一旦检测到政治、色情、暴力、涉恐等违规内容，网关必须立即拦截请求，返回统一的合规错误提示，并记录安全审计日志。
3. **电信资质合规**：平台商业化运营前，必须依法申请并获得 **增值电信业务经营许可证（ICP 证、EDI 证）**。

## 第5章 技术架构与部署设计

### 5.1 整体技术栈

| 层次 | 技术选型 | 选型理由 |
| :--- | :--- | :--- |
| **网关与后端** | Go 1.22 | 极高的并发处理性能、极低的内存占用，原生支持高并发协程，适合构建高性能 API 网关。 |
| **控制台前端** | Next.js 15 + TailwindCSS | 优秀的 SSR/ISR 性能，利于 SEO 优化，开发效率高，组件库生态丰富。 |
| **核心数据库** | PostgreSQL 16 | 强大的事务支持，高并发下行锁（`FOR UPDATE`）性能稳定，支持 JSONB 格式，便于存储复杂的 API 响应。 |
| **高速缓存** | Redis 7.2 | 用于存储 API Key 鉴权缓存、限流令牌桶、高频配置，保障网关毫秒级响应。 |
| **密钥管理** | HashiCorp Vault | 工业级密钥安全托管，避免敏感 Key 明文写在代码或数据库中。 |
| **监控告警** | Prometheus + Grafana | 实时监控系统 QPS、延迟、错误率，可视化展示平台健康度。 |

### 5.2 核心计费与高并发设计
* **余额扣减原子性**：
  为避免多并发请求导致的用户钱包“超卖”或余额不一致，系统在扣费时，使用 PostgreSQL 的事务结合行锁：
  ```sql
  BEGIN;
  SELECT balance FROM wallets WHERE user_id = 'usr_123' FOR UPDATE;
  -- 业务层校验余额是否充足 --
  UPDATE wallets SET balance = balance - 12500, last_updated = NOW() WHERE user_id = 'usr_123';
  COMMIT;
  ```
* **分布式限流**：
  网关限流采用基于 Redis 的**令牌桶算法**。限流规则动态下发，支持按用户级别、API Key 级别、模型级别进行多维度限流控制。

## 第6章 迭代规划与技术债务

### 6.1 短期迭代规划 (1-3个月)：Phase 1 - 核心骨架搭建
* **核心网关**：基于 Go 1.22 完成网关核心路由及适配器设计，支持 DeepSeek、Qwen、Kimi 及 OpenAI 协议。
* **高可用流式**：实现 SSE 流式转发与流式计费，建立自动故障转移机制。
* **高精度钱包**：完成 PostgreSQL 数据库表结构设计，实现微美元（Micro-USD）高精度原子计费。
* **基础控制台**：完成控制台基础版，支持用户注册（含防刷人机校验）、API Key 自助创建与钱包余额查询。

### 6.2 中期迭代规划 (3-6个月)：Phase 2 - 商业化与合规
* **支付合规集成**：集成微信支付、支付宝及企业对公转账，支持人民币到微美元的动态汇率换算。
* **企业级控制台**：推出多 API Key 独立风控、用量可视化图表、在线 Playground。
* **内容安全审查**：网关层上线双向内容合规审查模块，拦截违规输入输出。
* **发票与财务**：上线自助开票系统，支持增值税电子普通发票自动开具。

### 6.3 长期迭代规划 (6个月以上)：Phase 3 - 生态与规模化
* **组织协作**：上线企业组织/团队管理，支持共享钱包与成员配额分配。
* **智能路由算法**：网关引入智能路由，根据历史延迟、实时成本、Prompt 长度自动选择性价比最高的供应商通道。
* **监控与可观测性**：全面接入 Prometheus + Grafana 链路追踪，建立自动化毛利分析系统。
* **私有化部署**：支持为大型企业客户提供私有化网关部署方案。

### 6.4 技术债务与重构防范
* **数据库迁移管理**：严禁手动修改生产环境数据库，必须引入 `golang-migrate` 或 `goose` 进行版本化管理。
* **敏感 Key 逐步迁移**：Phase 1 允许在数据库中加密存储 Key，Phase 2 必须强制迁移至 HashiCorp Vault 托管。
* **分布式缓存**：随着并发量上升，单机内存缓存需平滑迁移至 Redis 集群，网关设计需预留缓存接口抽象。
